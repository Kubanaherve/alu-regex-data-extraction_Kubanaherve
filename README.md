# ALU Regex Data Extraction

This is my regex data extraction project for ALU. I wrote a Python program that reads raw text (like data from an API) and extracts emails, phone numbers, URLs, and credit card numbers using regular expressions.

I also added some basic security checks because the raw text is untrusted — it could contain bad data or even malicious content, so I don't just blindly accept everything.

## Project Structure

```
alu-regex-data-extraction_Kubanaherve/
├── input/
│   └── raw-text.txt          # The raw messy text I'm extracting data from
├── src/
│   └── main.py               # My main Python script
├── output/
│   └── sample-output.json    # The extracted results (generated by main.py)
└── README.md                 # This file
```

## How to Run

Just run this from the project root:

```bash
python src/main.py
```

It reads `input/raw-text.txt`, extracts the data, and saves the results to `output/sample-output.json`. It also prints a short summary in the terminal.

No external packages are needed — I only used `re`, `json`, and `os` from the Python standard library.

## What Data I Extract

### 1. Email Addresses

I used this regex pattern to find emails:

```
[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}
```

What it means:
- `[A-Za-z0-9._%+-]+` — the part before the `@`, which can have letters, numbers, dots, underscores, etc. The `+` means one or more characters.
- `@` — the @ symbol.
- `[A-Za-z0-9.-]+` — the domain name, like `alueducation` or `gmail`.
- `\.[A-Za-z]{2,}` — a dot followed by at least 2 letters, like `.com` or `.org`.

After finding emails with the regex, I also check:
- There is exactly one `@` sign.
- There is something before the `@`.
- The domain has a dot in it.
- The domain doesn't have too many parts (to reject things like `test@alueducation.com.evil.com`).

### 2. ALU Email Classification

I check the domain of each email to classify it:

| Domain | Type |
|--------|------|
| `@alueducation.com` | ALU official |
| `@alumni.alueducation.com` | ALU alumni |
| `@si.alueducation.com` | ALU SI |
| `@alustudent.com` | ALU student |
| anything else | other |

I only match the exact domain — so something like `@alueducation.com.evil.com` would NOT be classified as ALU official.

### 3. Phone Numbers

I used this regex pattern for Rwandan phone numbers:

```
(?:\+250[\s-]*[0-9]{3}[\s-]*[0-9]{3}[\s-]*[0-9]{3})|(?:0[0-9]{3}[\s-]*[0-9]{3}[\s-]*[0-9]{3})
```

What it means:
- `\+250` — the Rwanda country code.
- `[\s-]*` — optional spaces or dashes between the digit groups, because people write phone numbers in different ways.
- `[0-9]{3}` — groups of 3 digits.
- The second part `0[0-9]{3}...` handles the local format like `0788 555 221`.

I normalize all phone numbers to the format `+250XXXXXXXXX` so they are consistent. I also check that the total number of digits is correct (12 digits after removing the `+`). If it's too short, like `+250 788`, I reject it.

### 4. URLs

I used this regex pattern:

```
https?://[A-Za-z0-9._~:/?#\[\]@!$&'()*+,;=-]+
```

What it means:
- `https?` — matches both `http` and `https`. The `?` makes the `s` optional.
- `://` — the standard separator after the protocol.
- The rest matches the domain, path, and other URL parts.

I only accept `http` and `https` URLs. I don't accept dangerous schemes like `javascript:` or `data:` because those could be used for attacks.

### 5. Credit Card Numbers

I used this regex pattern:

```
\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{1,4}
```

What it means:
- `\d{4}` — four digits. `\d` is the same as `[0-9]`.
- `[\s-]?` — an optional space or dash between groups.
- The pattern expects about 13-16 digits total.

After finding something that looks like a card number, I use the **Luhn algorithm** to check if it's mathematically valid. I did this because regex by itself can't tell me if a number is a real card number — it can only find things that *look like* card numbers. The Luhn check is a simple math formula that real card numbers pass.

## Security

I treat the raw text as untrusted because it's supposed to come from an external API. Here's what I did:

- **I don't execute anything** from the text. I don't use `eval()` or `exec()`. I only look for patterns.
- **I mask emails** — I only show the first letter and replace the rest of the username with `****`. For example, `aline.mukamana@alueducation.com` becomes `a****@alueducation.com`.
- **I mask credit card numbers** — I replace all digits except the last 4 with `*`. For example, `4111111111111111` becomes `************1111`. I don't want full card numbers showing up in my output.
- **I reject suspicious URLs** — I only accept `http` and `https`. Things like `javascript:alert('hello')` get ignored.
- **I reject fake ALU domains** — Something like `test@alueducation.com.evil.com` won't be classified as an ALU email.
- **I use Luhn validation** — Card numbers that don't pass the Luhn check are rejected, even if they look right.
- **I check input size** — I don't process files that are too large.

## Limitations

I want to be honest about what this project can and can't do:

- The email regex only handles common email formats. It doesn't cover every possible valid email according to the full RFC specification.
- Phone validation only works for Rwandan numbers (`+250` or `07XX` format). It won't work for other countries.
- URL extraction is basic — it handles common URLs but might not catch every edge case.
- The Luhn check only tells you if a number is *mathematically* valid. It doesn't tell you if the card actually exists or belongs to someone.
- This is an educational project, not a complete production security system. In a real system, you'd want much more thorough validation.
